# 裁决记录：批次四十五 b 房间循环（2026-09-14，AD-168）

**背景**：PRD `docs/product/prd-group-collaboration-v1.md`（2026-09-14 修订版）§B4。第一稿给了三档按钮（手动「转给…」/ `@` 自动路由 / 讨论表单），产品方否掉了：「**我应该不需要这么多操作**——里面有 abc 三个 agent，我进去发一句『你们针对…问题讨论一下』，或者『a 和 b 你们观点冲突了，辩论一下最后给我一个合适的答复』，就应该能跑起来；@ 可以保留。」本批按这句话实现。

**验收**：kernel **1769 / 73 skipped**（新增 32），仓库级 246，前端 **527**（新增 10），`npm run check` 全绿。**真机未验**，测试单 L3–L8 在 `docs/quality/test-card-batch40-density.md`。

---

- **AD-168 路由由「房间循环」驱动，替代 AD-153 的第一、二点。**

  AD-153 写的是「用户就是协调者，路由只有广播与定向，都由用户发起；Agent-to-Agent 的自动追问不做」。那条裁决的**理由**至今成立，它的**结论**不成立——产品方 2026-09-14 明确：成员必须能在这个窗口里共同工作、实际沟通配合，否则组没有意义。所以这一条不是推翻 AD-153，是把它守的东西换一种守法。

  - **AD-153 真正要守的是「任何一句话都追得到发起人」，而房间循环守得比它更严。** 它当时怕的是「A 的输出自动成为 B 的输入 → 时间线上出现没有人按过发送键的消息 → 出错要回溯得先还原一遍当时的策略」。房间循环没有策略可还原：**它只有一条固定规则**——用户说一句开一条线程（`epoch += 1`），队列按加入先后轮流，一人一轮，说完下一位。时间线上每一条成员发言都带 `epoch` / `round` / `speakerIndex` / `deliveredSince` / `deliveredTo`，**顺着 `epoch` 一定回得到那条用户消息**，顺着 `deliveredSince` 答得出「他当时看见了什么」。AD-153 那时的时间线反而答不出后半句——它根本不记成员说了什么（那个 bug 由批次四十五 a 修掉）。
  - **串行，不是并行。** 一轮内按队列顺序一个说完再投下一个。并行看起来快一倍，代价是两个人同时回一个**已经过时的房间**：B 看不到 A 刚说的话，于是两人各说各的，用户拿到两段互不相干的独白——那正是「协作」的反面。串行的另一半好处是成本可预测：每轮 = 队列长度次引擎调用。
  - **停下来有四种，各自说不同的话。** `final`（有人以「最终答复」开头收口）→ 那一条渲染成高亮卡，房间安静等用户下一句；`exhausted`（轮数到顶，默认 6、可改 1–20）→ 时间线上一句「N 轮到了，没有最终答复」；`idle`（一轮内没有一个人说出话）→ 静默停；`stopped`（用户按「停」）→ 不必再说话。压成一个 `stopped` 会让界面在「它给了答案」与「它转了六轮什么都没给」之间说同一句话。
  - **「停」不打断正在跑的那一位。** 他这一轮的回复照记（旁观者认的是引擎的终态，不是线程状态），房间只是不再投下一位。去打断等于丢掉一段已经付过钱的正文，而用户按「停」要的是「别再往下转」，不是「把刚才那句作废」。
  - **投不出去的那一位按「这一轮他没说话」算，立刻推给下一位。** 等一个永远不会来的 `run.completed`（成员暂停了、引擎没起来、上一轮还在跑）会把整个房间挂死，那比少一个人发言严重得多。一整轮没有一个人说出话时按 `idle` 停住——这同时覆盖了「全员略过」与「全员投不出去」两种。
  - **点名 = 队列。** `@名字` 与裸的显示名都认（产品方那句话是「a 和 b 你们辩论一下」，不该要求他学一个符号），解析用的是批次四十五 a 那张**共用的显示名表**——显示名同时是称呼与地址，两处各算一次会让 `@写手#2` 在两个人之间抛硬币。定向发送（`targetMemberIds`）等价于点名。没点到名 = 全体活跃成员。
  - **旁观者不单独投递，靠游标补齐。** PRD §B4 有半句说「每轮结束后给旁观者投一次增量」，本批**没有这么做**：那会让一个明说「这一轮你不说话」的成员每轮跑一次引擎，与 §B8 的 L4（「C 不说话」）和 §B4 自己那句「每轮 = 队列长度次引擎调用」都对不上。改为把 `lastDeliveredSequence` 记在**成员**上：C 下次被点到时，他收到的增量从他上次说话之后算起，A 与 B 那几轮都在里面——L4 要的「旁观增量生效」由这一个游标提供，一次引擎调用都不多花。
  - **`@` 接力不新开线程、不加轮。** 成员回复里 `@B` → B 提前到本轮的下一位；点到旁观者 → 把他拉进队列。仍受 `roundCap` 管，所以接力不能变成一条绕开兜底的路。**这一轮已经说过的人不再插一次**：「一轮 = 每人各说一次」是队列这个东西唯一的含义。
  - **投递内容只含已经公开的东西**（AD-154 保留）。房间增量（`room_delta`）是一段固定格式：你是谁 · 组里有谁 · 本轮发言人与旁观 · 自你上次发言以来房间里说了什么 · 三条约定（略过 / 点名 / 收口怎么写）。它从**组时间线**上读，而组时间线上从来没有成员的私有过程（工具入参、中途的思考都在各自会话里）。取哪些行用的是**白名单**（`message` / `broadcast` / `directed` / `member_turn` / `system`）而不是黑名单——「哪些东西会被送进别人的上下文」不该靠记得改一处黑名单来保证。略过的那一轮不进增量：「B 说：（略过）」是一句没有内容的话。
  - **状态落库，进程重启时收尾。** 线程状态与 `roundCap` 落在 Group 上（SQLite 迁移 v7 加 `settings_json` / `thread_json` / `last_delivered_sequence` 三列，走既有追加机制）。推进下一位靠的是挂在 Session Host 上的旁观者——**它是进程内的**，进程一没，库里那条 `running` 就是一句假话（组头说「轮到 B」而永远没人投给 B）。所以起来时把 `running` 一律收成 `stopped` 并在时间线上说一句为什么；**不替用户续上**，续上等于在他不在场时替他跑一次引擎。
  - **推进放在后台任务里，不在旁观者里直接投。** 旁观者是在**上一位那条会话的事件流里**被调用的，在那里 await 一次完整投递（最多两秒）等于把 A 的事件泵按住；这期间谁要停 A，停就等泵、泵在等 B，两边互相等着。本批第一版真的这么挂过，现象是测试在 `aclose()` 上永远不返回。
  - **端点只多一条。** `POST /groups/{id}/thread/stop`；`PATCH /groups/{id}` 认 `roundCap`（**设置**不是动作，所以跟标题走同一条路）；`GET /groups`（列表与详情）带上 `thread`。**没有**「转发」「讨论」端点——房间自己会转，用户只说话与按停。
  - **协调者仍然不做**（PRD §A6）：用户那一句话就是协调。等房间跑顺了再看要不要让某个成员常驻当组长。

- **AD-154 原样保留。** 房间说明与房间增量只含**已在组时间线上公开**的内容，不含任何成员的私有正文；Context Packet 仍然是只读汇编，端点上没有 `inject` 参数，也没有任何写路径。

- **信封仍然冻结：** AgentEventEnvelope v1.1 一个字没动。`kaus/group.changed` 多一个 `change` 取值 `thread_state`（与 `member_turn` 分开：那一条说「时间线多了一行」，这一条说「组头那行要改」——浮窗据它重取组列表拿新的 `thread`，不必为了看一眼「轮到谁」把整条时间线重取一遍），仍然走 `extension.event` 那个唯一出口。

- **wire 变化：** 新增 `POST /api/groups/{id}/thread/stop`；`GET /api/groups` 与 `GET /api/groups/{id}` 的组对象多 `settings`（`{roundCap}`）与 `thread`（`{epoch, round, status, speakerQueue, spectators, speakerIndex, awaitingMemberId, startedByMessageId, spokeInRound, passedInRound}`，从没转过是 `null`）；成员行多 `lastDeliveredSequence`；`kind="member_turn"` 的时间线行多 `epoch` / `round` / `speakerIndex` / `deliveredSince` / `deliveredTo` / `passed` / `final`（**取不到就不出现这个键**——不属于任何一轮的成员发言不该被编出一个「第 0 轮」）；用户那一行多 `epoch`。`PATCH /api/groups/{id}` 多收 `roundCap`。新 code：`invalid_round_cap`（400）。既有字段与既有端点形状一律未变，除下面这一条：

- **行为变化（既有端点）：** `POST /groups/{id}/broadcast` 与 `/members/{m}/send` 的响应体里，`deliveries[]` 现在是**这一刻**已经发生的那几行（串行之下通常只有队首那一位），其余随房间转下去回填到时间线的同一行上。顺序也反过来了：先落时间线再投递——房间增量是从时间线上读出来的，用户这句话不在时间线上，第一位成员就无从被告知它。批次二十六那条「先投递再落行」的理由（那一行要带 deliveries）由回填接手。

**就地补在 AD-168 里，不新开 AD 号。** 上面那条裁决的骨架——房间循环、串行、点名即队列、增量只含公开内容、进程重启收尾、推进走后台任务——**一条都没变**。变的只有其中一件事：**房间怎么知道自己做完了。** 它当初就是这条裁决里最薄的一处，真机第一次用就塌了。

### 第一版为什么失败（真机证据）

产品方拿它做的第一件事是：**让组里的成员互相介绍一下自己。** 房间一路聊到了 6 轮上限，末尾落下那句「6 轮到了，没有最终答复」。他的原话：

> 「6 轮明显是拍脑袋的数，简单问题太多，复杂问题不见得该停；该取决于**是否得出了明确的成果**。现在 agent 之间永远会互相聊下去，没有停止机制，也没有对产出结果的定义。」

这个判断是对的，而且比「调一下那个数」更深一层。第一版把停止交给了两个东西：

1. **一个拍脑袋的轮数上限。** 它的问题不是 6 太大或太小——是它**与「做完了没有」毫无关系**。一问一答的房间转 6 轮是浪费，一个真要辩出结论的房间在第 6 轮被硬切是丢掉成果。同一个数不可能同时是这两件事的答案。
2. **「谁想收口就主动写『最终答复』」。** 这一条更要命：它把停止权交给了**最不可能行使它的一方**。一个客气的助手永远还有一句可补充的——补一个角度、呼应一下上一位、再确认一次需求。真机上那一次，三个成员连着六轮谁都没写那四个字，因为对它们来说「还能再说一句」永远是成立的。

共同的根因是一句话：**「做完了没有」被设计成了 agent 要主动想起来的动作。** 靠自觉的东西在多 agent 房间里不会发生。

### 新机制：三条

- **① 表态是每轮必填的一格，不是自觉。** 每条回复的最后一行必须是 `[状态] 可收口` 或 `[状态] 还需继续 — 还差：<一句话>`，**这句要求写在每一轮的房间增量里，每轮重申**（`ROOM_CONVENTIONS`）。纯函数 `parse_status` 取正文**最后一个**以 `[状态]` 开头的行（取最后一个而不是第一个：模型常常先把格式复述一遍再真的写一行），判出 Ready / Continue(gap) / Missing 三态。这不是让模型多说一句话——是把一个隐式的判断变成一个**每轮都在 wire 上的字段**，房间因此每一轮都答得出「还有人觉得没完吗」。

- **② 全体可收口 → 进收口轮，而不是等谁自觉。** 一轮走完，队列里每一位的最新表态都按可收口计时，房间**单独发一条**给队首里仍活跃的那一位：`closing_prompt()` 那段逐字指令 + 开启这条线程的用户原话。它的回复标 `final=true, phase="closing"`，渲染成那张已有的高亮卡，线程转 `final`。**收口是一个动作，有明确的执行者和明确的输入**，不再是「希望有人想起来」。两条配套：
  - **收口那一轮不计入 `round`**（它不是讨论的一轮）；
  - **`round == 1` 全体可收口时跳过收口**，直接安静 + 一句「大家都说完了」。一问一答那一轮本身就是答案，再让一个成员把三段自我介绍「收成结论」只是多花一次引擎、多一条废话。**这一条与安全阀一起，正是第一版两头都做不到的那件事：简单问题一轮完事，复杂问题不会被硬切。**

- **③ 轮数降格成安全阀。** 默认 6 → **12**，上限 20 → **50**。它不再是「预期停止点」，只防成本失控——正常讨论碰不到它。碰到了也不再干停：`round + 1 > roundCap` 时**强制收口**（同一条收口轮），文案从「N 轮到了，没有最终答复」改成「到达安全上限（N 轮），已让 X 收口」。原来那句话最坏的地方是把一次正常兜底说成了一次失败，而用户手上什么都没有。**现有组的旧值照旧**（迁移不动数据），库里存着 6 就还是 6。

另有一条跨轮判据（PRD §B4 终止 3）：**某成员连续两轮的 `gap` 归一化后相等 → 他此后按可收口计。** 他在原地打转。没有这一条，一个反复说「还差同一件事」的成员能把房间一路拖到安全阀——那正是第一版的病，只是换了个说法。gap 必须归一化（NFKC、去空白、去标点、剥掉「还差」那个引子），否则这条判据等于永远不成立：模型两轮写同一件事时几乎不会一个字节都不差。

### 「Missing 按 Ready 计」——这一批唯一一个刻意偏保守的取舍

成员没写那一行表态时，房间**按「可收口」处理**，并在 `metadata.statusMissing` 上留痕、在收口那条 system 里点名说明。

它显然可以反过来（没表态 = 还要继续）。选现在这一边，理由是两种错的代价不对称：

- 早停错了，用户说一句「继续」房间就回来了——他有一个**一秒钟的修法**；
- 该停没停，用户只能干等，而**干等正是第一版被打穿的那件事**。

代价是真实的：模型偶尔忘了写那一行，房间就会早收口一轮。所以它必须**看得见**——收口那条 system 会点名说「X 没有按格式表态，按可收口计」。一个看得见的偏保守默认，好过一个看不见的偏激进默认。

同一条精神管着解析本身：`[状态]` 只认**半角逐字**（`［状态］` / `【状态】` 都不认）。这一行是**格式**，模糊匹配等于把格式退回自觉；而一旦某种写法被悄悄接受，房间说明里那句「必须是」就成了一句不准确的话。写错的那一行落进 Missing，代价是早停一轮——正是上面那条已经接受了的代价。

两个词都出现在同一行时**按「还需继续」判**（与 PRD 列举的顺序相反，刻意的）：「还需继续 — 还差：确认结论能不能可收口」读成 Ready 是这条规则最贵的一种错，而反过来几乎不会发生。

### 终止的六条与它们之间的一处冲突

六条判据全部收在纯函数 `advance_thread` 里（**不散在路由层**：散了的话「房间为什么停了」就得读一遍路由才答得出，而它正是这一批最该能单测的东西）。路由层只负责把「他说了什么」翻成三个事实：略过 / 主动收口 / 这一轮的表态。

PRD 的六条里有一处冲突：**终止 5（一轮内没有一个人说出话 → `idle`，不收口）与终止 2（全体可收口 → 收口）**。略过没有表态行，按 Missing 算就是「全体可收口」，于是一轮全员略过会同时命中两条，而它们给的答案相反。实现取**终止 5 优先**：大家都没说话，压根没有东西可收——让一个成员去「把上面的讨论收成答复」而上面一句话都没有，是一次注定尴尬的引擎调用。

### 收口失败：不重试

收口那一轮投递失败或跑失败 → 写一行「收口没有成功：<原因>」并 `stopped`，**不重试、不换人**。重试等于再花一次钱去赌一件刚刚失败的事；换人等于换一个人来失败（收口人是从队首挑的，不是从「能跑的人」里挑的）。而用户此刻要的不是房间再试一次，是知道「它没收成」——否则组头一直挂着「正在收口」，永远等不到那张卡。

### §B10 的两个真机 bug

- **B10-1 打字说「停」。** 真机截图里用户在输入框打了「停止」，房间把它当成一条普通消息投给了成员，成员回「已停止。」——而房间其实还在转。修法：用户消息去空白后**全等于** `停` / `停止` / `stop` / `Stop` / `STOP` / `暂停一下` 之一时走停止路径，不落 `broadcast`/`directed` 行、不投递、不开新 epoch，只写一条 system「已停止（你说了『…』）」。**广播与定向两条路都挡**（真机那一次是定向发的，只挡广播等于只修了一半，而且正好不是出事的那一半）。

  **只认全等，不做包含**——这是这条规则敢存在的全部理由。它不是在猜用户的意思：词表是封闭的短词表，任何长于该词的句子都不命中，所以「不要停下来继续讨论」照旧是一条普通消息。大小写也不折（`stop` / `Stop` / `STOP` 各自在表里列着）：折起来等于把这张表从「这几个词」偷偷扩成「这个词的所有写法」。

- **B10-2 显示名上 wire。** 时间线上两个同名成员都显示 `media`，而房间说明里它们是 `media` / `media#2`——后端那张表算了重名后缀，却没上 wire，于是界面一个真相、引擎另一个真相（截图里成员自己说「@media#2 负责执行与质检」，用户却分不出那是谁）。修法：`GroupMemberWire` 加 `displayName`（后端那张表算好的，含后缀），前端 `memberDisplayName` 改为**优先用它**。

  这不是「两处写法不一致」这么简单：前端只看得见一个成员，**看不见组里有没有第二个同名的**，所以它根本算不出后缀——本地推断那一支只能作为老后端的退路留着，不可能算对。成员栏、时间线气泡、投递明细、组头「轮到 X」现在全走同一份名字。

### wire 变化（信封仍然冻结）

`AgentEventEnvelope v1.1` 一个字没动，`kaus/group.changed.change` 沿用 `thread_state`（没加新取值）。

- `ThreadStatus` 多一个 `closing`；`exhausted` **后端不再写入**，留着只为读得懂旧数据；
- `thread` 多 `phase` / `closerMemberId` / `endedReason` / `lastGap` / `stuckMembers` / `roundStatus`；
- `kind="member_turn"` 的行多 `phase`（只有收口那一条有）/ `statusGap` / `statusMissing`，**取不到就不出现这个键**；
- `GroupMemberWire` 多 `displayName`；
- `PATCH /groups/{id}` 的 `roundCap` 范围 1–20 → **1–50**，默认 6 → **12**；
- **端点一条没加**（收口是房间自己的动作，不是一个用户要按的按钮）。

### 这一批没做

① 真机未验（L6 改写 + L10–L13）；② 表态词只认中文（`可收口` / `还需继续`）——英文界面下的房间说明仍是中文那一段，等真机上出现英文引擎再说；③ 「用户说一句『继续』把刚早停的房间接回去」没有特别处理，它就是一条新消息、一条新线程（这正是「早停可恢复」那句话的实现，不必再多一条路径）；④ §B6 协调者仍然不做（PRD §A6）。

## 2026-09-14 第三次修订（批次四十七）：可收口是粘性的

**就地补在 AD-168 里，不新开 AD 号。** 上面两节的骨架——房间循环、串行、点名即队列、增量只含公开内容、每轮必填的表态、收口是一个有执行者的动作、轮数只是安全阀——**一条都没变**。变的仍然是同一个地方：**「全体可收口」这件事该怎么判。** 第二次修订把它从「自觉」改成了「每轮必填的一格」，但那一格每轮清空、全员重投，于是判据仍然要求一次**巧合**。

**验收**：kernel **1828 / 73 skipped**（新增 22），仓库级 246，前端 **554**（新增 6），`npm run check` 全绿。**真机未验**，测试单 L14 / L15 在 `docs/quality/test-card-batch40-density.md`。

### 产品方的提问

> 「A 觉得可收口了，结果 B 提出一个错误点或新辩论点，这时 A 是继续回答还是不再回复？」

这是一个关于**规则**的问题，不是一个关于某次对话的问题——而第二次修订的实现对它只有一个隐含答案：A 会再答。`round_status` 每轮清空，新一轮里 A 重新被投递、重新表态。

### 失败模式：礼貌性乒乓

顺着那个隐含答案往下推一步就看得见问题：

```
第 1 轮   A：可收口          B：还需继续（提了个新点）
第 2 轮   A：还需继续（礼貌地回应了 B）    B：可收口（满意了）
第 3 轮   A：可收口          B：还需继续（又想到一点）
第 4 轮   …
```

两个人**永远错开一格**。`everybody_ready` 那个 `all()` 看的是**同一轮**，而这两个人从来不在同一轮点头——房间因此凑不齐终止 2，只能干等 12 轮安全阀，每一轮都是真金白银的引擎调用。

这不是模型不听话，恰恰相反：**它是两个客气的助手各自正确行事的必然结果。** A 被问到就该回答，B 发现新点就该提。第一版的病是「一个客气的助手永远还有一句可补充的」；第二次修订治好了「他自己不肯停」，却留下了「他被别人叫住就会重新开口」——同一个病换了个位置。

### 修法：把「已收口」做成单调只增的集合

`RoomThread` 加 `ready_members`：**本线程内已经表过态可收口的成员**（含被判「原地打转」的）。每轮的**有效发言者** = 队列里不在这个集合中的那些；集合里的人不投递、不占引擎调用。

**为什么这样能保证收敛，而不是又一次巧合**——三句话：

1. **集合只增不减。** 每一轮里每个还在说话的人只有两种结局：说「还需继续」（集合不变）或按可收口计（集合 +1）。没有任何一条路径会把人从集合里拿出来。
2. **有效发言者因此单调不增**，而它是一个有限集（队列长度）。
3. **它一旦为空，房间就收口**（`round ≥ 2`）。而它不空时房间只会继续，每一轮至少不后退——所以要么某一轮集合满了（正常结局），要么在安全阀之前一直有人明说「没完」，那时收口也是对的。

这就是「一次巧合」与「一个单调过程」的差别：前者要求 N 个人在**某一轮同时**点头（概率随 N 与礼貌程度一起掉），后者只要求每个人**各自在某一轮**点过头一次。

**唯一的出口是 `@`。** 任何一位的发言里点到集合中的 X → X 被移出集合，并插到**本轮**队列的下一位（沿用既有 `_relay` 的插队语义，没另造一套）。它不破坏上面那条论证：把人拿出来需要**另一个人明确写出他的名字**，那是一次有主的、看得见的动作，不是每轮自动重投。

**召回刻意不受「这一轮他已经说过了」那条限制**（那是四十五 b 的 `_relay` 给接力定的规矩）。理由很具体：B 正是**读完 A 这一轮说的话**才发现 A 讲错了，如果要等下一轮才能召回，那句「@A 你第二点错了」就会晚一整轮——而 A 这时已经不在队列里，下一轮根本不会有他，召回就永远不会发生。实现上这要求 `_relay` 把**当前发言人的下标**一起返回：召回一个排在他前面的人会把队列往前挪一格，不一起返回的话接下来那句「下一位 = 下标 + 1」就指到别人身上了。

**用户自己发的新消息照旧开新 epoch**，`ready_members` 随整条线程归零——不需要为它写一行清理代码。这也正是「早停可恢复」那句话在这一批的样子：房间收早了，用户说一句「继续」，所有人都回来。

### 单人守卫

一轮结束时有效发言者只剩 1 位、**且他这一轮谁也没点名** → 按收敛处理，进收口（`ended_reason = "lone_speaker"`）。**一个人对着空房间自言自语不是讨论。** 没有这一条，「A、B 都收口了，C 还想说」会一路转到安全阀，而 C 每一轮都是在回应一个没有人的房间。

两条边界是刻意的：

- **他点了名就不算自言自语**——被点的那位会被召回，房间接着转（而且这时候队列里真的有两个人了）。
- **队列里本来就只有一个人不算「只剩」。** 用户定向问某一位、或组里只有一位成员时，那是一次正常的一对一问答，照旧一轮一轮转到安全阀。守卫防的是「其他人都退场了」，不是「你只叫了一个人」。

`round == 1` 就触发时走 `idle` 而不是收口——「一轮就问完了不再多一条总结」那条对这条路同样成立。

### 一处连带的口径修正

「一轮里没有一个人说出话 → `idle`」（终止 5）原来比的是 `passed_count >= len(queue)`。粘性之下**队列长度不再等于这一轮会说话的人数**：A 早就收口了，剩下 B、C 两个都略过，拿 3 去比 2 会把它读成「还有人说了话」。改成比**这一轮真开口的人数**（`spoke_in_round`），在粘性之前的那些情形里两者完全等价。

### `round_status` 与 `stuck_members` 的新位置

- **`round_status` 每轮清空的行为保留，但它不再是终止判据。** 判据改看 `ready_members`。它现在只剩两个用处：本轮的日志 / 调试，以及收口那条 system 里点名「谁没按格式表态」。**这带来一个已知的缩水**：一位成员在第 1 轮忘了写那一行，他这一轮就退出了队列，等房间真的收口时他已不在当轮的 `round_status` 里——那句点名因此只说得出**触发这次收口的那一轮**里谁没表态。没有为此加一个线程级的 `missing_members`：PRD 这一段列的新字段只有 `ready_members` 一个，而缩水的那半句是一句补充说明，不是一条不变量。真机上如果发现用户确实读不懂房间为什么早停，再补也不迟。
- **`stuck_members` 并入 `ready_members`。** 「连续两轮同一个 gap → 此后按可收口计」这条语义一个字没变，只是实现合成一处：退不退出队列只看一个集合。`stuck_members` 那一格留着，但它现在只回答「他是**为什么**退出的」——被判原地打转与自己说可收口，在界面上不是同一句话。

### 房间说明多的那一条

`ROOM_CONVENTIONS` 每轮重申的那几条加一条：**「别人说了可收口就不再发言了；你要他回来回答，必须写 @他的名字。」**

它不是可有可无的提示。粘性改的是**规则**，而规则必须让参与者知道，否则模型会对着一个已经退场的人接着提问，而那个人永远不会回答——房间于是转出一段谁也没在听的独白。同一个理由让房间说明里「本轮发言人」那一行改成只列**有效发言者**：给成员一份永远等不到的名册，和那句新约定是互相打架的两句话。

英文界面下房间说明仍是中文那一段（第二次修订的「这一批没做」②），本批不动。

### wire 变化（信封仍然冻结）

`AgentEventEnvelope v1.1` 一个字没动，`kaus/group.changed.change` 沿用 `thread_state`。

- `thread` 多 `readyMembers`（老后端没有这个键 ⇒ 缺席，不是空数组）；
- `ThreadEndedReason` 多 `lone_speaker`；
- **端点一条没加，既有字段一个没改。**

前端只多一段组头文案：`running` 那一档后面挂「· 已收口 N 人」，**只在 N>0 时出现**（AD-71）。它是这条 wire 上唯一看得见收敛的东西——那个数只增不减，用户于是分得出「房间在往收口走」与「两个人在互相客气」。时间线一个新控件都没加。

### 这一批没做

① 真机未验（L14 / L15）；② 上面那条 `round_status` 缩水（点名只说得出触发收口那一轮的 Missing）没有补线程级字段；③ 「已收口 N 人」不可点开——看是哪几位要去读时间线上各自那条表态；④ 召回没有次数上限：理论上两个人可以互相 `@` 到安全阀，但那需要两边**每一轮都明确写出对方的名字**，与礼貌性乒乓（谁都没点名、房间自己重投）是两件事，真机上出现了再说。
