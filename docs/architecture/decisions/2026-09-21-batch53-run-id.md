# 裁决记录：批次五十三 run id 跨进程唯一 ＋ 时间线归并 ＋ 三处简报勘误（2026-09-21，AD-174）

**背景**：第一次多厂家真机验收的报告 `docs/quality/reports/2026-09-21-multivendor/REPORT.md` §6.1 / §6.2。四台引擎三家体系同组跑通，但挖出了**第一条真机暴露的内核缺陷**（前面几批暴露的都是房间层或界面层）：MV-01，run id 在后端重启后撞名。产品方 2026-09-21 裁定按**方案 A**（编号换成跨进程唯一的东西）修，不走方案 B（启动时读回最大编号）。

这一批三件事：MV-01（内核）、时间线翻旧被重取吞掉（界面）、三处简报勘误 ＋ 一条排错行（文档）。

**验收**：kernel **1849 / 79 skipped**（批次五十二基线 1838/79，+11 条），仓库级 **246**（不变），前端 **582**（基线 573，+9 条），`npm run check` 全绿。**真机未验**——测试单新增 **L23**（后端重启后组继续正常收发），在 `docs/quality/test-card-batch40-density.md`。

---

- **AD-174 run id 的唯一性由**注入**的令牌保证，不由进程内计数器保证；翻译器保持纯函数。**

  ### 缺陷是什么形状

  `kernel/drivers/acp/translator.py` 此前这么拼 run id：

  ```python
  self._run_index += 1
  self._run_id = f"{self.context.session_id}:r{self._run_index}"
  ```

  `_run_index` 是**翻译器实例内**的计数器，初始化为 0。新建会话时 `session_id` 本身是新的，撞不上；**撞车发生在续接**：后端重启之后拿同一个 `native_session_id` 续上，计数器却从 0 重新数——于是「重启后的第一轮」又叫 `<session>:r1`，和重启前那一轮同名。像叫号机重启后又从 1 号叫起，而大厅里已经坐着一个 1 号。

  **咬人的地方不在 run id 自己，在拿它当键的那几处。** run id 是幂等键的一半（`(conversation, run)`），组时间线靠它判「这一轮是不是我在等的那一轮」，`_run_started_at` 靠它找这一轮的开跑时间。撞名不会报错，它只是**悄悄指向另一轮**——真机上的表现是「写手的 `run.completed` 已经到了，组却还在等写手」（报告 §2）。

  ### 为什么唯一性必须从外面注入

  `AcpTranslator` 的类注释写着「有状态但**没有 IO**：同一串输入永远产出同一串输出」，`drivers/acp/tests/test_purity.py` 与一条新增的确定性断言一起守着它。随机数与时钟**都是 IO**，所以修法不能是在 `begin_run()` 里 `uuid4()`——那等于用「唯一」换掉「可重放」，而可重放是这个翻译器存在的理由（同一串报文重放两次必须逐条给出同样的 eventId，AD-37）。

  于是：**令牌由 Driver 在接会话时现铸，翻译器只负责把它拼进字符串。** Driver 本来就做 IO，铸在那里不破任何东西。

  ### 落法

  - `AcpTranslationContext`（frozen dataclass）加一个**必填**字段 `run_token: str`。必填而不是给默认值：全仓只有两处构造点（`driver.py` 与 `tests/test_translator.py`），必填逼出一次完整审计，也挡住以后有人忘了传——而忘了传的后果是跨进程撞名，那正是本条要修的病。
  - `begin_run()` 拼成 `f"{session_id}:{run_token}:r{index}"`。**`:rN` 保留**：它仍旧读作「这次接上之后的第 N 轮」，人读日志时要的就是这个。唯一性在中间那一段。
  - **令牌在 `AcpDriver` 接会话那一处现铸**：`uuid.uuid4().hex[:8]`，每次 attach 都是新的。
  - **刻意不用 `handle.runtime_id`**：它也是进程内计数器（`f"{backend_id}-runtime-{n}"`），重启后一样从 1 开始——换一个同样的毛病不算修。

  形状举例（**真跑出来的**一对：同一条会话，中间隔了一次「重启」）：

  ```
  重启前  5e4934a6-5f09-4afe-884f-824ca8d1f4a8:7958d6db:r1
  重启后  5e4934a6-5f09-4afe-884f-824ca8d1f4a8:3b97c440:r1
          └────────── native session id ─────────┘└ token ┘└┘
                                                            这次接上之后的第 1 轮
  ```

  会话 id 是同一个、轮次都是第 1 轮——**只有中间那一段不同**，撞名就是在这里被挡住的。

  ### 为什么不选方案 B（启动时读回账本里的最大编号）

  两条：① **账本被裁剪过时它照样撞**——事件有保留期（v1.0 §8.5），旧事件被清掉之后读回来的「最大编号」比真实的小，于是新一轮又会叫一个用过的名字，而这种撞名比重启撞名更难发现（它不发生在一个显眼的时刻）；② 每次拉起会话多一次查询，换来的还是一个「取决于账本完整性」的保证。注入的令牌不查任何东西，也不取决于任何东西。

  ### 历史数据不迁移

  老账本里已有的撞名 run id **留在那儿**。迁移要改写已经落库的事件（信封头里的 `runId`）——那是在改一份只追加的账本，代价与风险都远大于收益，而收益只是让几条老数据好看一点。

  代价是 `_run_started_at` 那道兜底要一直留着：它改成**从尾往前扫**（`reversed(rows)`）。id 唯一之后方向本无所谓；在撞名的老数据上，从头扫命中的是重启**前**那条（更旧），从尾扫命中的是**较新**那条，后者是两者中更接近真相的一个。扫描本身搬成了纯函数 `app.collaboration.member_turns.run_started_at`，docstring 里写明「这是对历史数据的兜底，不是主要防线」——一道没有解释的兜底迟早会被人顺手改回去（它看上去毫无意义：id 都唯一了，方向当然无所谓）。

  ### 这把尺子挂进了契约套件

  `drivers/contract_tests/suite.py` 新增 `test_run_ids_never_repeat_within_one_conversation`：**同一条会话里 run id 不得重复**，每个 Driver 都要被它量。连带发现 Mock 夹具自己在演撞名——所有剧本用写死的默认 run id（`run-text` 之类），同一条 Conversation 编排两次会播出两条同名的 `run.started`。夹具就是这里的「后端」，run id 由后端给，所以改成**每次编排现编一个**。例外只有 `external-http-shaped`：那一条的 run id 来自被重放的外部报文，换掉它就换掉了「这条外部流能无损映射」这件事本身的证据。

  「重启后续接」那条端到端路径在 ACP 驱动层（`drivers/acp/tests/test_driver.py`）：attach → 跑一轮 → **换一个全新的 `AcpDriver` 实例**（两个进程内计数器都随之从头数）→ 用同一个 `native_session_id` 再 attach → 两轮的 run id 不等。

  ### 四条审计的结论（只报告，不改动）

  1. **全仓别的 run id 生成点**：没有。ACP 这一处是唯一的**生成**点（`translator.py`）。Mock 的 run id 来自剧本（夹具），Hermes 的来自服务端。
  2. **Hermes 原生驱动没有这个形状**：它的 run id 是**服务端给的**（`drivers/hermes/driver.py` 从提交回合的响应体 `payload["run_id"]` 里取，取不到就 `DriverError`），不含任何进程内计数器，后端重启也不会让网关重新发同一个 id。**这一批不动 hermes。**
  3. **`runtime_id` 那个进程内计数器**：会被**落库**——`session_host.py` 把它写进 lease 的 `backend_process_id`（R-10 的 reconcile 按它判存活），也出现在两处 API 返回体（`session_views.py` / `session_router.py` 的 `runtimeId`）。但它**不被拿来跨进程匹配**：lease 的 `backend_process_id` 只在同一个进程的生命周期内有意义，reconcile 判的是「这个进程还活着吗」。另外 Mock Driver 早就踩过一次并绕开了（`drivers/tests/test_mock_event_ids.py`：eventId 原本含 `runtime_id`，改成用每实例一次性的 uuid4 种子，**不进 `runtime_id`**，因为后者会出现在 API 返回体里）。**结论：不是当前的缺陷，但它是同一类东西，改不改等裁。**
  4. **前端没有任何地方解析 run id 的形状**：`runId` 在前端全程是不透明字符串（`lib/timeline/reducer.ts` 的事件类型、`lib/groupsApi.ts` 的回执与 `member_turn` 的 `runId`），没有一处按 `:r` 切、没有一处 `match` / `slice`。所以 run id 变长不影响任何一处渲染。

- **时间线：重取改成按 `sequence` 归并，不再整份替换**（口径已有，只是落错了地方）

  `GroupWorkspace.tsx` 的时间线 effect 在**任何一次**重取上都 `setMessages([...最近 50 条])` 整份替换，而它挂在组级流的任一条变更（`changeToken`）与自动刷新（`autoToken`）上。于是用户点「加载更早」往前翻了三页，房间里任何人发一句话——三页全没了，视口跳回最近 50 条，`nextBefore` 也退回最近一页的边界，那枚已经消失的「加载更早」又冒出来。**翻旧是用户花力气做的事，一条别人的发言不该把它撤销。**

  - 归并写成导出的纯函数 `mergeGroupTimeline`，按 `sequence` 去重（组内单调递增）。同一个 `sequence` 出现两份时以**新取回来的那份**为准——消息的投递与轮次状态可能被改过，旧的那份是过时的快照。
  - **`nextBefore` 的口径改成「我手上最早那条之前还有没有」**，不是「最近一页之前还有没有」。只有当这一页真的比手上最早那条还早时才采用它给的游标。已经翻到头（AD-173：本页最早行 `sequence` 为 0 → 后端回 `null`）之后再重取，按钮不会变回来。
  - 重取、「加载更早」前插、乐观发送回填**三处走同一个函数**，规则不再各写一遍。
  - 归并要拿「我手上**现在**有什么」，而 effect 闭包里的是取数**发起那一刻**的（用户在等隧道的那几秒里点了「加载更早」，闭包看不见），所以加了一份同步镜像 `held`；它带着 `groupId`，换组时这一页是「头一次取」而不是重取，整份替换。
  - `unseenCount` 用序号数、不用长度差这条性质没被破（归并之后再确认了一遍：前插两条旧的，`unseenCount` 仍是 0）。

- **三处简报勘误 ＋ 一条排错行**（都是编排方写错的，真机替我们发现）

  - **MV-04**：Antigravity 的安装步骤漏了同包的 `localharness_external`。解压出来的不止 `agy_acp_server.par` 一个文件，少了它 `session/new` 报 «Could not find default localharness binary»。`docs/ops/backends.md` 与 `presets.py` 的 `notes` **两处都改了**，并写上真机上绕过去的那条 `ANTIGRAVITY_HARNESS_PATH`。
  - **MV-05**：登录那句是错的。原文写「先在终端跑一次 `agy`，ACP 服务端复用缓存凭据」——那是官方 headless 文档对 `agy -p` 说的话。真机上 `agy` 已登录，ACP 端**仍然单独弹了浏览器授权**：它用的是**另一份 Google OAuth**。改成照实说：`agy` 的登录**不够**，ACP 服务端首次连接会自己发起一次 Google OAuth（浏览器），需要用户当场完成。**没有编一条我们没取证过的登录命令**——真机只证到「另一份 OAuth、会弹浏览器」这一层，就只写这一层（AD-71）。`login_command="agy"` 字段留着（它确实是这家的 CLI 登录入口），但 notes 说清了它不够。
  - **MV-08**：`/api/backends` 回的是**对象**不是裸数组（`{"backends": [...], "count": n}`）。`docs/quality/ops-brief-2026-09-21-multivendor.md` 那段 `python3 -c` 把它当裸数组遍历，跑起来直接炸；改成从 `["backends"]` 里取。
  - **MV-03**（顺手）：`backends.md` 的排错表补一行——某个适配器自带的那个引擎二进制 spawn 报 `-88` 时，用 `CLAUDE_CODE_EXECUTABLE` 指向本机已装好的 CLI 绕过去（真机上就是这么过的）。

- **wire 变化**：**没有。** `AgentEventEnvelope` v1.1 一个字段都没动；`runId` 的**取值形状**变长了（多了一段 `:<token>`），但它对所有消费者都是不透明字符串（审计 4）。

- **行为变化**：① 新产生的 run id 形如 `<session>:<token>:r<N>`，老账本里的仍是 `<session>:r<N>`，两种共存且互不干扰；② `_run_started_at` 在撞名的老数据上取到的从「重启前那条」变成「较新那条」；③ 组时间线的重取从替换变成归并，`nextBefore` 的口径跟着变。

- **没动的**：`server.py`、`room.py` 的 `next_round_queue` / `advance_thread` / `resolve_mentions`、hermes 驱动（审计点 2 只出结论）。

- **待办**：① **真机未验**——测试单新增 L23，MV-01 的真机复现路径就是它；② 审计点 3 那个 `runtime_id` 计数器没改（它落库进了 lease 的 `backend_process_id`，也出现在两处 API 返回体），等裁；③ 老账本里的撞名 run id 不迁移，那道「从尾扫」的兜底要一直留着；④ 真机报告里的 MV-02（首次介绍时 Antigravity 回 MCP 初始化错误）这一批没碰。
