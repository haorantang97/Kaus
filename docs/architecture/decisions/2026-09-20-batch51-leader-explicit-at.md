# 裁决记录：批次五十一 组长的路由只认显式 `@`（2026-09-20，AD-172）

**背景**：第二次外派的真机报告 `docs/quality/reports/2026-09-19-group-2/REPORT.md`。AD-171 落地之后的第一份记录，两个问题都答成了「是」——⑱ 里第 2 轮真的跑起来了（组长写 `@评审 …下一轮由你发言`，`thread.round` 1→2），成员互 `@` 没能单独开出第 2 轮。但 §8 编排方复核挑出一件新的事：

> ⑱ 第 1 轮组长那句 `@评审 请回应打杂最后的追问`，`mentions=[评审,打杂]`——**打杂是被裸名匹配捎进去的**（组长只 `@` 了评审，「打杂最后的追问」是在谈论他）。

那一场里它恰好无害（辩论本来就该两人都说），但暴露的是结构：**AD-171 把路由收进组长一个人手里之后，「组长谈论谁」与「组长点名谁」就成了同一件事**。而组长是主持人，它必然要在话里提到成员——「评审的质疑成立」「打杂说的那个边界已经清楚了」——宽尺子下每提一个人就多拉一个人进下一轮。终止 3（组长不点人 → 停）因此又一次被一句自然的话悄悄否掉，只不过这回否掉它的是组长自己。

产品方裁决（2026-09-20）：**谁在说话决定用哪把尺子**（任务书 `docs/tasks/batch51-leader-explicit-at.md` §0）。PRD `docs/product/prd-group-collaboration-v1.md` 随之出**第六次修订**（§A3 / §A5 / §B4 / §B6）。

**验收**：kernel **1829 / 79 skipped**（批次五十基线 1819/79，+10 条），仓库级 246，前端 **562**，`npm run check` 全绿。**真机未验**——测试单新增 **L21**，在 `docs/quality/test-card-batch40-density.md`。

- **AD-172 组长的路由只认显式 `@名字`；用户的开场话仍认裸名；成员的话本来就只记录不路由。**

  这一条**只动一处读法**：`next_round_queue` 读组长那条时用哪把尺子。`resolve_mentions` 的**默认行为一个字没改**（长名优先、命中就挖掉、回成员表顺序），AD-171 的其余各条、AD-169 的骨架、AD-168 的房间循环都没动。

  ### 为什么不是「一把尺子改窄」

  最省事的做法是把 `resolve_mentions` 整个改成只认 `@`，一处改完全场生效。它不成立的理由是**两边的人不一样**：

  - **用户那一边**：产品方给的原话是「A 和 B 你们观点冲突了，辩论一下」。他是人，是非程序员，`@` 对他是一个要学的符号——AD-169 当初认裸名就是为了这一句。为了修组长那一边而让用户学符号，是拿被服务的人去迁就实现。
  - **组长那一边**：它每一轮都读到 `LEADER_NOTE`，那段话**本来就在教它写 `@名字`**，⑱ 里它也确实这么写了。对它来说这不是新负担，只是把「我写了 `@`」与「房间照着做」这两件事对齐。
  - **成员那一边**：AD-171 之后它们的话根本不进队列，用哪把尺子都不改变谁说下一句；`metadata.mentions` 是取证，取证要的恰恰是**宽**——「他提到了谁」比「他 `@` 了谁」更接近人读那一行时想问的问题。

  所以这一版留两把尺子，而**谁在说话决定用哪把**。这是一条能一句话说清的规则，也是唯一能同时满足三边的。

  ### 落法

  - **`resolve_mentions(text, members, *, explicit_only=False)`**：`True` 时候选只有 `f"@{name}"`，**不再回退到裸名**；长名优先与「命中就挖掉」的逻辑共用同一段代码（`@写手#2` 照旧不会同时点中两个写手）。默认 `False`，所以用户开场那句（`_route`）与落 `metadata.mentions` 那处（`_record_member_turn`）**一个参数都不传**，行为不变。
  - **`next_round_queue` 是唯一传 `True` 的地方**。`resolve_everyone` 不动——它本来就只认带半角 `@` 的 `@所有人` / `@everyone`（裸的「所有人」在中文里太常出现）。
  - **`LEADER_NOTE` 末尾加一句逐字**：「只有写了 @ 的名字才算点名，正文里提到的名字不算。」不加这一句的话，组长这一边的规则与它看到的行为就对不上——它会以为自己只是提了一句打杂，而房间把打杂拉进了下一轮。
  - **组长那条 `member_turn` 另记 `metadata.routed`**（新键，上 wire）= 真正进了下一轮队列的那几位，按队列顺序，**不含组长自己**（它是无条件追加到队尾的，算进来这一格就不说明任何事情）。与同一行上的 `mentions` 并排，时间线因此答得出「组长提到了打杂，但打杂没被路由」——这正是 §8 那件事，也是测试单 L21 验的两格。

  ### 几处实现里自己拍的板

  - **`routed` 与 `final` 走同一条回填路**（`_mark_routed` / `_mark_final`，upsert 同一行、`sequence` 不动）。下一轮队列要等整轮走完才算得出来，落行的时候还不知道——这与终止 3 回头标 `final` 是同一个时序问题，所以用同一个解法而不是新发明一个。
  - **`routed` 只在真的进了下一轮时才写**：组长收口（终止 2/3）、触顶收口（终止 4）那几轮队列算了也没用，写上去等于说了一件没发生的事。空就不加这个键（与 `mentions` 同一条口径）。
  - **不含组长自己**，上面说过；另一种写法（照抄 `speakerQueue`）会让每一条都至少有一个名字。
  - **`mentions` 仍旧用宽尺子**，没有顺手跟着收窄。它是取证不是路由，而这一批全部的意思就是这两件事得分开——把它也收窄，L21 就没东西可验了（`mentions` 与 `routed` 会永远相等）。
  - **PRD §A5 / §B6 顺手改了两处**：§A5 原本只说「之后每一轮的 `@` 只认组长写的」，§B6 逐字引着 `LEADER_NOTE` 的旧文本。同一份 PRD 里自相矛盾比措辞旧更危险（AD-171 也是这么处理的）。

- **AD-171 / AD-169 / AD-168 的其余各条原样保留。** AD-171 的「路由只在组长手里」没有被削弱，这一条是给它加了一个「怎么算点名」的定义。

- **AD-154 / 信封原样保留**：房间说明与房间增量仍只含已在组时间线上公开的内容（`public_entries` 那张白名单一个字没动）；`AgentEventEnvelope` v1.1 没动；`kaus/group.changed` 的 `change` 没有新取值。

- **wire 变化：** `member_turn` 行多一个可选的 `routed: string[]`（只出现在组长那条，且只在真开了下一轮时），前端 `GroupMessageWire` 同步加了字段但**不渲染**。端点一条没加，没有删字段。

- **行为变化（既有端点）：** 第 2 轮及以后的队列只由组长那段话里的 `@名字` 决定。对存量组是**收紧**：此前组长在正文里裸提某人就会把他拉进下一轮，现在不会——组长不写 `@` 就停。用户那句开场话不受影响。

- **待办：** ① 真机未验（测试单新增 L21）；② 组长会不会因为「只有 `@` 算数」而变得更爱点人（多点一个 `@` 比少点一个便宜），只有真机答得出——真答歪了，下一步是看 `roundCap` 与终止 4 那条安全阀，而不是再加一句约定；③ 成员正文里的 `@名字` 仍未渲染成 pill（AD-169 的待办 ③，本批照旧没做）；④ 房间说明仍旧只有中文。
